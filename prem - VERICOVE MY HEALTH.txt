# PHASE 4 — BUILD THE ADAPTIVE QUESTION ENGINE

This is the most important functional requirement.

The question engine must be dynamic.

Do not create a static questionnaire containing a predetermined number of questions.

The AI should select the next relevant question using the user's existing answers and the information still required.

## 4.1 Conversation workflow

Implement the following logical stages:

### Stage 1: Understand the concern

Ask the user what they are experiencing.

Allow natural language responses.

Examples:

- "I've been feeling unusually tired."
- "I've noticed discomfort in my lower abdomen."
- "I've been experiencing headaches."
- "My sleep pattern has changed."

Do not force users to choose from a predefined symptom catalogue.

### Stage 2: Understand the experience

Based on the primary concern, identify relevant information such as:

- Location.
- Onset.
- Duration.
- Frequency.
- Sensation or nature of the symptom.
- User-reported severity.
- Changes over time.

Ask only questions that are relevant.

### Stage 3: Understand the context

Depending on the symptom, ask about relevant context.

Possible topics:

- Previous occurrences.
- Existing health conditions.
- Relevant medications.
- Previous medical consultations.
- Relevant personal health history.

Ask sensitive questions only when clinically relevant.

Explain why sensitive information is needed.

Do not collect unnecessary personal information.

### Stage 4: Explore associated symptoms

Identify relevant associated symptoms based on the user's responses.

The engine must:

- Avoid repeating questions.
- Avoid asking irrelevant questions.
- Adapt follow-ups to new information.
- Recognize contradictory answers.
- Ask for clarification when necessary.

### Stage 5: Review and complete

Determine whether enough information has been collected.

If the information is sufficient, generate a structured summary.

If more relevant information is needed, continue asking questions.

If an urgent safety concern is detected, prioritize appropriate professional-care guidance instead of continuing routine questioning.

## 4.2 Dynamic stopping condition

Do not use a fixed question count.

Implement a structured completion evaluation.

A session may end when:

- Relevant required fields have been collected.
- The user explicitly chooses to finish.
- The user chooses to pause.
- A safety condition requires escalation.
- Further questioning is unlikely to improve the summary.

Never prolong the conversation simply to collect more information.

## 4.3 Structured conversation state

Maintain a structured session state.

Example:

{
  "sessionId": "session-id",
  "primaryConcern": "pelvic discomfort",
  "collectedInformation": {
    "location": "lower abdomen",
    "onset": "three days ago",
    "frequency": "intermittent",
    "severity": null,
    "associatedSymptoms": []
  },
  "missingInformation": [
    "severity",
    "associatedSymptoms"
  ],
  "safetyStatus": "not_assessed",
  "nextQuestion": null,
  "sessionStatus": "active"
}

This is an illustrative schema. Design the actual schema according to the application.

## 4.4 AI orchestration

Do not let an unrestricted LLM independently invent medical interview procedures.

Use a controlled orchestration architecture:

1. Receive the user's answer.
2. Validate and normalize the response.
3. Update structured session information.
4. Evaluate relevant missing information.
5. Run clinician-reviewed safety checks.
6. Select an appropriate next question from a structured question framework.
7. Generate conversational wording using the LLM.
8. Validate the generated response.
9. Return the question and available answer options.
10. Persist the session state.

The LLM should control natural conversational phrasing, not independently define clinical safety rules.

Use structured JSON responses with schema validation.

Handle malformed AI responses and provider failures without losing user data.

## 4.5 Example conversation branches

Create test scenarios for at least:

- Fatigue.
- Headaches.
- Pelvic discomfort.
- Menstrual irregularities.
- Sleep disturbances.
- Digestive discomfort.

These are testing scenarios, not diagnostic pathways.

Each scenario should demonstrate how answers change the next question.

Include an unknown-symptom fallback that supports natural language rather than forcing users into existing categories.

## 4.6 Medical safety

Build a clinician-reviewed safety framework.

It must:

- Check urgent warning signs early.
- Avoid delaying urgent-care recommendations.
- Never diagnose a condition.
- Avoid unsupported treatment recommendations.
- Avoid medication dosage recommendations.
- Distinguish user-reported information from AI interpretations.
- Clearly communicate uncertainty.
- Recommend appropriate professional evaluation when warranted.

Do not invent clinical thresholds or emergency protocols.

Use trusted, reviewed medical guidance for any safety rules implemented.

If clinical rules have not yet been validated, clearly mark them as unavailable for clinical use rather than presenting them as reliable.

- Present one natural-language question at a time with selectable answer cards and a clear Continue action. Show the selection state and allow the user to change it before continuing.
- Include “I’m not sure” and “Not applicable” only where appropriate; provide “I’d rather not say” for sensitive questions.
- Add a quiet “Something else? Add a few words” alternative that reveals a small contextual field only when chosen. Voice input may populate this field, but the user must be able to edit the transcript before submitting.
- Do not make free text the primary response mechanism, force users to type, or automatically submit a partial transcription.

## Adaptive question engine

- Represent each question as validated structured data: unique ID, clinical information category, conversational wording, selectable options, answer-to-state mapping, relevant follow-up categories, and completion relevance.
- Select the next useful question from the concern category, selected answers, missing relevant information, and resolved/unknown/not-applicable answers. Do not walk through a fixed questionnaire list.
- Prevent unnecessary repeats. Skip questions that no longer add useful information, such as impact follow-up after the user says the experience has stopped.
- Preserve all answers in a structured session. Let the user edit earlier selections without restarting, and keep the summary synchronized.
- When enough useful information has been gathered, show a summary and offer both “Continue with Mira” and “I’m satisfied.” Continue opens a refinement question without discarding prior answers. Support repeated refinement until the user is satisfied, without an artificial round limit.
- Validate every displayed question and option set. If AI is later connected, reject malformed output and use a validated deterministic fallback. Never render model HTML.
- The current project has no AI provider configured. Do not label deterministic demo prompts as live AI analysis.

## Voice identity and behavior

- Mira’s intended voice is calm, warm, feminine, mature, conversational and clear, with a neutral accent in the user’s selected language where available. Avoid robotic, childlike, high-energy or exaggerated delivery.
- Use a configured neural voice only through a supported provider and server-held credentials. Never invent endpoints or voice identifiers, expose provider keys in the browser, or claim browser speech has neural quality.
- Without a configured provider, choose the best language-matched device speech voice available, prefer a suitable feminine voice when the browser exposes one, and clearly label it as a device fallback. Allow voice selection where supported.
- Provide replay, pause, stop, mute/on-off, and speech-speed controls. Keep question speech and visible text aligned. Do not read answer options automatically, autoplay without consent, or speak over the user’s response.
- If speech recognition is unavailable or denied, preserve the card-based flow and offer the optional text alternative with a clear status.

## Summary and safety

- Keep the transition loop available: question → selected answer → adaptive question → reviewed summary → optional refinement → updated summary.
- Separate reported answers from AI-generated interpretation. Never store an unreviewed interpretation as a confirmed medical fact.
- If clinician-reviewed safety guidance is not configured, state that it is unavailable for clinical use. Do not invent emergency thresholds or rules.
